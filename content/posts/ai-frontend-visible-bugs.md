## 现象：每一块都对，拼起来不能看

让 AI 写个页面，它交付得飞快：编译通过，控制台干净，逻辑也对。打开一看——间距忽大忽小，空数组渲染出一块破碎的 UI，暗色模式下赫然一块白底，长文本把卡片撑破。

大多数人的归因是「AI 审美差」或者「提示词没写好」。都不对。我踩了足够多的坑之后发现，AI 生成前端的肉眼 bug 不是能力问题，是**三个结构性缺陷**，每一个都能从大模型的工作方式推导出来。

这篇文章讲这三个原理，以及从每个原理推导出的那层解法。技巧是鱼，推导是渔。

## 原理一：它是采样器，不是查找器

同一个 prompt「做个登录页」，AI 今天给你 Inter 字体加紫色渐变，明天给你圆角卡片加淡蓝背景。不是它在变，是**输出本来就是一个概率分布**，肉眼 bug 是采样落到了分布的坏区域。

理解这一点，所有「描述侧」技巧就统一了——它们的本质全是同一件事：**收窄输出分布的熵**。

**给参照物，比给形容词有效一个数量级。**「像 Linear 的侧边栏」把分布直接锚到一个具体模式上；「简洁大方现代」是无效信息，因为每个采样点都自称简洁大方。

**负面清单比正面描述稳定。**「间距要舒适」是模糊操作，「文字超长必须 truncate，不许撑破容器」是精确操作——直接把坏区域从分布里挖掉。AI 对「不要做 X」的遵守程度出奇地好，我自己的规则库里最值钱的全是否定句。

**给真实数据，别给理想数据。**肉眼 bug 的大头不是样式错，是数据形态错。列表组件在真实数据下要面对空数组、超长文本、null 字段、3 条和 1000 条——不说，AI 就按理想数据写，理想数据里没有这些。每个界面至少说清四态：loading / empty / error / success，交互组件再加 hover / focus / disabled。

**锁死组件库白名单。**shadcn/ui 只有一套 Button，AI 自由发挥能写出一百种。组件白名单是最大的单一防 bug 措施——它把取值空间从连续压到了离散有限。

一个推论值得记住：**约束防的是抖动，不是提上限**。没有约束时同样的 prompt 这次好下次坏，你遇到过的「不稳定」全是这个。约束是把下限抬起来的。

## 原理二：自回归局部性——它越写越偏

LLM 从左到右逐 token 生成，注意力随距离衰减。写到页脚时，页面顶部的间距约束已经在几万 token 之外。所以 AI 生成的东西有一个典型特征：**局部永远合理，整体逐渐漂移**。每一块单看都对，间距体系崩了、组件风格乱了、同一个 Button 写了两遍。

这直接推导出任务切分的解法：

**先骨架，后样式。**第一轮只要布局层级——flex/grid 结构、栅格、组件占位。确认结构对了再填视觉细节。道理很简单：把全局决策放在 context 最前面一次性固定，后面的生成是「看着答案写」，漂移的锚点始终在场。

**逐组件交付。**导航、列表、表单分开验收。把单次生成的长度压到局部性半径以内，漂移就没有跑道。

**规范进文件，不进对话。**对话会滚出上下文窗口，文件每次全量注入。设计约定写进项目 CLAUDE.md，别靠「我们刚才说过的」。

**版本锚定。**有一类肉眼 bug 和描述质量无关：AI 脑子里的 Tailwind 是 v3，你项目里是 v4，class 名对不上，样式静默失效——不报错，就是「不对劲」。它还会自信地使用不存在的组件和 props。解法还是约束：

```markdown
- Tailwind v4 + shadcn/ui（2026-01 版），禁止使用其他版本的 API
- 使用组件前必须先读 components/ui/ 下对应源码确认真实 props
```

## 原理三：修复循环的收敛性——视觉迭代是个搜索问题

前两条还只是「写得不对」，真正让人崩溃的是另一件事：你指出问题，AI 修，修完 A 坏 B，再修，B 好了 C 裂了，越修越乱。

这不是运气差，是这个循环**不满足收敛条件**。视觉迭代本质是迭代搜索：当前状态 → 修复 → 比较 → 再修复。搜索收敛需要一个硬条件——**每一轮的「变好还是变坏」必须可判定**。不满足就会发散。

三个实践从这里推导出来：

**给 AI 装眼睛。**AI 默认的工作闭环是「写完 → 编译通过 → 交付」，视觉 bug 不报错、测试不挂，它自己不知道错了。截图闭环把闭环改成「写完 → 截图 → 自己看 → 自己改」。具体做法是在需求里写死验收动作：

```
完成后用浏览器打开页面，对上述每个状态（含 375px 视口）逐一截图自查，
发现问题自己修，修到无肉眼问题再交付。
```

工具现成：Claude Code 配 chrome-devtools MCP 或 playwright-mcp，AI 就有了浏览器。这一条比所有描述技巧加起来都重要——它把「你发现问题再描述给它」的往返整个省掉了。

**波及面控制。**AI 修视觉 bug 的高频二次事故是顺手改了共享样式，弄坏别处的页面。规则：修 bug 前先 grep 这个样式类/组件的使用面，报出影响范围；改完对受影响页面截图对比，不只看目标页。本质是保证修复是局部扰动，不污染搜索空间的其他区域。

**一轮只修一类问题。**一次多目标修复的 diff 无法归因，等于盲搜。间距问题和暗色模式问题分开修。

**验证分层。**截图自查有真实的 token 和时间成本，成本高了 AI 会开始偷偷跳过自查。写明分层：单点样式改动只截单视口单状态；新页面跑状态 × 视口矩阵；重构和依赖升级上全量视觉回归——Playwright 的 `toHaveScreenshot` 直接把「看起来对」变成 CI 里可断言的东西。

## 拼起来：一套能自洽的体系

三层原理对应三层解法，串成完整工作流：

```
上游    任务切分        先骨架后样式，逐组件交付        ← 对抗局部性
        描述显式化      数据形态 + 状态穷举 + 负面清单  ← 收窄分布
中游    版本锚定        版本号写死，用前读源码          ← 堵静默失效
        波及面控制      先查使用面，改完对比受影响页    ← 保收敛
下游    截图闭环        逐状态自查，修完再交付          ← 补感知
        验证分层        小改单截图，重构上回归          ← 控成本
事后    规则生长        每个 bug 转成清单/断言/回归测试  ← 积累
```

最后一行最容易被忽略，也最值钱：**你的 bug 历史是最贵的训练数据**。每个肉眼 bug 做三选一——能穷举的，CLAUDE.md 负面清单加一条；能断言的，E2E 加一个断言；会复发的，视觉回归锁住。坚持三个月，你的规则库就是量身定制的，比任何通用最佳实践都锋利。

## 附录一：工具清单，直接套

按三层对号入座：

**感知层（给 AI 装眼睛）**
- [microsoft/playwright-mcp](https://github.com/microsoft/playwright-mcp)：标准答案，accessibility tree 只花 2-5KB 而不是截图的 500KB
- chrome-devtools-mcp：要查 console、网络、性能时用
- [web-infra-dev/midscene](https://github.com/web-infra-dev/midscene)：自然语言 E2E + 视觉断言

**约束层（让第一次就写对）**
- Anthropic 官方 `frontend-design` skill：必装，强制先定审美方向，禁默认紫渐变
- [nextlevelbuilder/ui-ux-pro-max-skill](https://github.com/nextlevelbuilder/ui-ux-pro-max-skill)：240+ 风格、127 字体配对
- [Leonxlnx/taste-skill](https://github.com/Leonxlnx/taste-skill)：可调旋钮，控制 AI 有多「有主见」

**收敛层（视觉回归）**
- Playwright `toHaveScreenshot()`：零成本起步，关键页面先锁上
- [americanexpress/jest-image-snapshot](https://github.com/americanexpress/jest-image-snapshot)、[oblador/loki](https://github.com/oblador/loki)、[reg-viz/reg-suit](https://github.com/reg-viz/reg-suit)

**目录**：[wilwaldon/Claude-Code-Frontend-Design-Toolkit](https://github.com/wilwaldon/Claude-Code-Frontend-Design-Toolkit) 收了 70+ 工具按目的分类，找新东西从这翻。

一个冲突提醒：官方 frontend-design skill 会建议 CSS variables 和自定义样式，如果你的项目像我一样锁死 Tailwind + shadcn，记得在 CLAUDE.md 里声明「样式规则优先于 skill 建议」——设计方向采纳，实现走组件库。

## 附录二：为什么我不给组件上向量检索

聊到前端 AI 化，常有人建议给组件库建向量索引做 RAG。我的结论是不做，原因在 embedding 的机理里。

embedding 是有损压缩：一整段代码压成一个一千多维的点。而前端代码恰好是**骨架高度重复**的文本——列表、卡片、表单、弹窗，只换变量名和文案，骨架几乎不变。压缩之后，大量结构不同但骨架相同的组件落成了几乎同一个点。检索时余弦相似度最高的一批，往往是「长得像」而不是「用得上」——假阳性成片。

对比之下，LLM 读 context 做的是 token 级的逐字交互比对，分辨率远高于「预压缩后比对」。所以 token 预算够的时候，**grep 拿十个文件全塞 context，比向量召回三个「最像的」更可靠**。同一套数学（内积 + top-k），attention 是每层都在跑的精读，ANN 是一次性的粗筛——粗筛该给精读递材料，而不是替精读下结论。

自建组件检索的场景不是不存在（几百个业务组件跨仓库），但优先级应该倒着来：先符号索引和组件名过滤，不够再加 BM25，最后才考虑 dense 向量——而且要按单组件切 chunk。多数团队直接从第三步开始，是把这个顺序做反了。

## 最后：可直接抄的模板

```markdown
做 XX 页面
- 约束：沿用现有 Next.js + shadcn/ui + Tailwind（v4，2026-01），禁止自创组件
- 数据：[贴真实 JSON，含空数组、超长文本、null 样例]
- 状态：loading 用 skeleton；空态「暂无 XX」+ 引导按钮；失败错误卡片 + 重试
- 交互：点击行 → 跳详情；提交失败 → toast，按钮防连点
- 响应式：桌面双栏，<768px 单栏，侧边栏收起为抽屉
- 负面清单：长文本 truncate；不出现横向滚动条；暗色模式核对一遍
- 验收：用浏览器逐状态截图自查（含 375px 视口），修完再交付
```

判断这套体系有没有长在你身上，看能不能秒答这几个问题：为什么负面清单比正面描述稳定？为什么 AI 写的页面局部都对整体不对？什么迹象说明修复循环在发散、该停手？你的项目里约束、感知、收敛三层，哪层缺了 bug 最多？

答不上来也没关系——回到对应的那一节，那三个原理值得读第二遍。
